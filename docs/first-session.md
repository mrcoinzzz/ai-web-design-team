# Your first session with the team

[Back to the README](../README.md)

You don't need to know how to design a website or organize AI agents. Describe what you're trying to do, and Alex will coordinate the work and explain the result.

Want to see the result first? Browse the [Clearfile redesign](../examples/clearfile/README.md) or [Northline new build](../examples/northline/README.md). Both are fictional practice sites with actual screenshots and recorded local checks.

## Meet your team

- **Alex — Design Lead:** your main point of contact. Keeps the work focused and brings the advice together.
- **Sam — Messaging & CTA:** helps visitors understand what you offer and what to do next.
- **River — Visual Design:** helps the site look coherent through layout, colors, type, and imagery.
- **Kit — Clarity & Accessibility:** checks whether the site is understandable and usable, including relevant mobile and keyboard interactions.

These are named AI responsibilities, not people or four separate apps. You use one skill in your existing assistant. When independent AI reviews are available, Alex can delegate; otherwise Alex applies the same specialties directly and tells you.

## 1. Set it up once

Follow the [setup guide for your tool](setup.md). The original four coding tools use a project skill folder; OpenClaw and Hermes have native installation commands. Then give your assistant access to the website or project you want to work on. You don't need to configure individual team members.

If the setup steps are unfamiliar, open the downloaded team folder in your coding assistant and ask:

```text
Help me install this AI Web Design Team skill for my website project.
Use the setup guide in docs/setup.md. Ask me which tool and project
folder to use if that isn't clear. Preserve any existing installation.
```

## 2. Start with one page

Select the skill using your tool's [invocation instructions](setup.md), then add:

```text
Alex, this is my first time using an AI design team. Please review my
homepage and explain the most useful improvements in plain language.
Don't change the website yet. I'll provide its URL or screenshots.
```

Give Alex the website URL, screenshots, or the local project to inspect. One sentence about your business and what visitors should do is helpful—for example, “I'm a tutor and I want parents to book an introductory call.” You can also say what you like and want to keep.

If you don't have a website yet, say:

```text
Alex, help me build my first website for a local tutoring business.
Parents should understand the lessons and contact me to book a call.
Keep it simple, explain the important choices, and build a local preview.
```

Alex will need an editable project for a build. A local preview lets you inspect the work; it doesn't by itself publish the website or connect a working contact service.

## 3. Know what to expect

Alex should briefly explain what will be reviewed, ask only for missing information that matters, and begin. The relevant specialties inspect the evidence, and Alex returns one prioritized set of changes with reasons.

Alex first establishes whether this session can inspect the evidence, edit the intended project, render a preview, and use independent reviewers. You don't fill out a checklist. If only screenshots are available, for example, Alex can review them while explaining that live form behavior can't be verified.

You should be able to tell which pages were inspected, what to improve, and what couldn't be checked. A screenshot can reveal layout issues; it cannot prove that a form submits correctly. The team should make that distinction clear.

## 4. Steer the work naturally

Continue in the same conversation:

| What you want | What you can say |
| --- | --- |
| A clearer explanation | “Alex, explain the first recommendation without design jargon.” |
| Better words | “Sam, suggest a clearer headline. Keep our product claims accurate.” |
| A layout review | “River, focus only on the mobile layout. Review only.” |
| Easier forms | “Kit, review whether our contact form is clear and usable.” |
| Two specialties | “Sam and Kit, review the signup page. Leave the visual design for later.” |
| Apply selected advice | “Alex, implement recommendations 1 and 3, and check the affected behavior.” |
| Lower usage | “Use one agent and apply River's visual-design lens.” |
| Explore the look | “River, show two small directions using the same content. Explain the tradeoffs and wait for my choice.” |
| Keep preferences consistent | “Keep the quieter direction we chose, the blue palette, and the existing logo.” |

You don't have to use names. “Review the copy” and “Check the mobile layout” work too. Mentioning a name doesn't create a separate conversation or automatically authorize changes. Keep the skill selected or its context available when starting a new session.

You can give River simple preferences: “Keep the colors,” “Less crowded,” or “I like this site's typography.” River turns them into concrete choices and keeps them in the current brief for follow-ups. A clear brief or small edit doesn't need an extra design-selection step.

## 5. Review the result

For implemented work, Alex should show the preview or changed files and explain the checks performed and any remaining gaps. You can ask for changes in everyday language: “That feels too busy,” “Keep the original colors,” or “Make the offer easier to understand.”

You remain in control of the scope. Ask for advice, a separate concept, or implementation as needed. Independent reviewers can use more of your assistant's allowance; “use one agent” keeps the work in one agent.
