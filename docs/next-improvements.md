# Where to improve next

These are proposed priorities, not completed features. The next gains should make the existing team easier to trust and direct.

## 1. Show a complete example and test it with newcomers

Publish one existing-site redesign and one new-site build with the actual brief, before/after or initial/final screenshots, meaningful decisions, and behavior checks. Use an authorized project or a clearly labeled fictional fixture. Ask someone unfamiliar with the team to follow the first-session guide and record where they get stuck.

This would demonstrate what Alex, Sam, River, and Kit actually deliver. Current package tests prove installation behavior; the illustrative review and behavioral scenarios do not establish design quality. Keep the evidence honest, including failures and checks that could not be run.

## 2. Make setup problems understandable immediately

Add a brief capability check at the start of substantive tasks: can this session inspect the site, edit the intended project, render a preview, and delegate? Explain only gaps that affect the request and identify the next useful step. For example, screenshot-only access permits visual advice but leaves form behavior unverified.

The team already has evidence limits and a single-agent fallback. The improvement would be a consistent, tested first-run experience across the documented hosts, with successful discovery and one real task recorded for each. It should not become a mandatory checklist the user has to fill out.

## 3. Help people express design preferences

Let people give a few likes, dislikes, and examples in ordinary language. When a broad redesign is genuinely ambiguous, River could offer two small, meaningfully different directions with tradeoffs before scaling one across the site. For narrow requests or an established brand, proceed with the existing direction.

Keep the chosen typography, spacing, imagery, tone, and retained brand elements in the existing brief. Use that context in follow-ups so people don't repeat themselves. Avoid introducing another persona, permanent memory requirement, or automatic approval checkpoint for every change.

OpenClaw and Hermes installation guidance is now available in the [setup guide](setup.md). Those instructions are documentation-verified; live-host evaluations remain part of priority 2.
